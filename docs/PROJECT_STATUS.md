## M0 — World Engine

**Status: verified development baseline; full product acceptance remains open.** Both packs compile, persist and pass the authoring smoke. The web UI can create, explain, lock, preview, snapshot/regenerate, restore a snapshot as a new revision, fork, search/open saved Worlds, export/import `.mhworld`, and upload/download custom World images. The import API validates archive paths, sizes, checksums, schema, identities, parent references and image bytes, then assigns independent IDs. PostgreSQL stores image bytes by digest and World revisions carry the image references. Remaining M0 work includes entity-level image assignment/rendering, blob garbage collection, deeper migration/rollback testing, and the full manual checklist on a clean database. The UI edit prompt could not be completed through browser automation; CUSTOM/LOCK was verified through the live API and persistence readback.

## M1 — Realm, Campaign, Session and Character

**Status: playable local baseline, not production access control.** Two browser contexts completed the Fantasy lobby and Character flows. Session PIN is five digits, Realm scoped, expires at session end, and cannot authorize protected GM routes. A campaign GM key is generated separately, stored as a hash, and required for session creation and GM commands. Character values and exact pack compatibility are checked server side. Each guest receives a random participant token at join; only its hash is stored. Participant commands and private Check reads require this token. Session WebSocket authentication uses the first message, and Check notifications reach only the assigned player and GM. The guest browser owner key remains a local bearer identity. World authoring, Realm authentication, rate limiting, richer roles and token recovery remain open before untrusted hosting. Existing participants created before the token migration need to rejoin. Single active Pack configuration remains a deployment constraint.

## M2 — Generic game runtime

**Status: M2.2–M2.5 baseline implemented and locally verified.** Declarative Action steps compose Check, Roll, Resource and Effect; target policies cover none, self, one actor and multiple actors. The HTTP layer delegates execution to `packages/game-runtime`. Action and Encounter mutations persist events and state together in one PostgreSQL transaction with actor and Encounter version checks. Stale commands return 409 without events. Actor initialization now inserts its state and event atomically. Standalone Check creation and resolution now persist their events in transactions; concurrent roll requests return the first saved result. Encounter ordering supports none, fixed, rolled, attribute and custom policies; Pack configuration selects the policy. Turns and rounds emit lifecycle events, and effects emit tick/expiry events. Fantasy and Cyberpunk contain declarative composed action examples.

Session NPCs come from validated Pack actor templates, persist in the actor state table, and share Action and Encounter commands with player actors. They can optionally reference a compatible entity in the Campaign's materialized World; their runtime mechanics remain Pack-defined. The GM can change the roster of a live Encounter without resetting its current turn. Only one live Encounter per Session is allowed. A full verifier detects Actor/Encounter divergence; verified checkpoints allow shorter replay of later events. Offline commands repair finished-Session Actor/Encounter state and standalone pending/resolved Check rows from events, with separate audit records; Check verification is GM-only and Check repair requires stopped servers. Idempotency receipts cover Action, Encounter, roster changes, NPC creation, Actor initialization and Check creation. Pack loading now validates executable runtime capabilities, bounded Dice, numeric fields, and Action references before starting a Session. The two bundled Packs declare numeric Character abilities, with a zero modifier for older Characters missing them. NPCs are not yet independently editable or removable; arbitrary third-party Packs, linked-entity revision reconciliation, and multi-node realtime remain open. These gaps prevent a production or full gameplay acceptance claim.
